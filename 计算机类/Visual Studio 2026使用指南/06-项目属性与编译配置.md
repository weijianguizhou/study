# 06-项目属性与编译配置

前面几章里，`/std:c++20`、`/MD`、`/O2` 这些开关都是一句带过。这一章把它们全部展开——**项目属性页是 Visual Studio 里信息密度最高的地方**，也是绝大多数"玄学编译错误"的真正源头。读完这一章，你应该能做到：看到一个编译开关就知道它在哪个页面，看到一类报错就知道该去改哪一项。

---

## 1. 属性页的入口与结构

### 1.1 三种打开方式

| 方式 | 路径 | 适用 |
|------|------|------|
| **右键项目** | 解决方案资源管理器 > 右键项目 > **属性** | 最常用 |
| **菜单** | **项目 > 属性** | 键盘流 |
| **快捷键** | 选中项目后按 `Alt+Enter` | 最快 |

> **注意**：**属性页是"项目"级别的，不是"解决方案"级别，也不是全局设置**。解决方案右键没有"属性"这一项。如果你在找 `/std:c++20` 却翻到了 **工具 > 选项**，那永远找不到——那里管的是 IDE 自己的行为。

### 1.2 顶部两个下拉框：新手最大的坑

属性页**左上角**有两个下拉框：

```text
┌─────────────────────────────────────────────────────────────┐
│  配置(C):  [ Debug        ▼ ]   平台(P):  [ x64         ▼ ] │  ← 看这里！
├─────────────────────────────────────────────────────────────┤
│  ▾ 配置属性                                                  │
│    ▾ 常规                                                    │
│    ▾ C/C++                                                   │
│    ▾ 链接器                                                  │
│    ▾ 清单工具                                                │
│    ▾ 生成事件                                                │
│    ▾ 调试                                                    │
├─────────────────────────────────────────────────────────────┤
│  右侧是当前"配置 × 平台"组合下这一项的取值                     │
└─────────────────────────────────────────────────────────────┘
```

**你在属性页里改的任何一项，默认只作用于当前选中的"配置 × 平台"组合。**

举个真实的翻车场景：

```text
1. 打开项目属性，看到配置是 Debug|x64
2. 把"附加包含目录"改成 D:\libs\include
3. 编译 Debug → 通过 ✅
4. 切到 Release 编译 → 报"无法打开源文件 xxx.h" ❌
原因：Release|x64 那一份配置里，包含目录根本没改
```

**两种正确做法**：

| 做法 | 操作 | 何时用 |
|------|------|--------|
| 一次改所有配置 | 把"配置"下拉切成 **所有配置**，"平台"切成 **所有平台**，再改 | 绝大多数情况 |
| 逐个配置改 | 分别切到 Debug/Release 各改一遍 | 确实需要差异时（如 Debug 用 `/Od`） |

> **提示**：改完之后，用 **配置** 下拉逐个切过去检查一遍。养成"改完扫一眼其他配置"的习惯，能省掉大量"Release 编不过"的排查时间。

### 1.3 属性页树形结构

```text
配置属性
├── 常规                     ← 输出目录、配置类型、工具集、语言标准、字符集
├── 高级                     ← 极少用（如 C++/CLI 属性）
├── 调试                     ← 命令行参数、工作目录、环境变量
├── VC++ 目录                ← 包含/库/可执行文件目录（建议改用 C/C++ 与链接器页）
├── C/C++                    ← 编译器开关（cl.exe）
│   ├── 常规                 ← /I /Zi /W4 /WX /MP /utf-8
│   ├── 优化                 ← /Od /O1 /O2 /Ox /GL
│   ├── 预处理器             ← /D /U /X
│   ├── 代码生成             ← /MD /MT /EHsc /GR /Gy /GS /arch
│   ├── 语言                 ← /std: /permissive- /openmp /Zc
│   ├── 预编译头             ← /Yc /Yu /Fp
│   ├── 输出文件             ← /Fa /Fd /Fo
│   ├── 浏览信息             ← /FR
│   ├── 高级                 ← /FI /TC /TP /showIncludes
│   └── 所有选项             ← 纯命令行视角
├── 链接器                   ← 链接开关（link.exe）
│   ├── 常规                 ← /LIBPATH /INCREMENTAL
│   ├── 输入                 ← 附加依赖项 /DEFAULTLIB /NODEFAULTLIB
│   ├── 清单文件             ← UAC 清单
│   ├── 系统                 ← /SUBSYSTEM /STACK
│   ├── 优化                 ← /LTCG /OPT:REF /OPT:ICF
│   ├── 嵌入的 IDL           ← 组件开发
│   ├── Windows 元数据       ← WinRT
│   ├── 高级                 ← /ENTRY /DYNAMICBASE /NXCOMPAT
│   ├── 命令行               ← 最终命令行预览
│   └── 所有选项             ← 纯命令行视角
├── 清单工具                 ← 清单生成
├── XML 文档生成器           ← /doc
├── 浏览信息                 ← 代码浏览数据库
├── 生成事件                 ← 生成前/链接前/生成后
├── 自定义生成步骤           ← 单文件自定义命令
├── 代码分析                 ← /analyze、clang-tidy（见第 9 章）
└── 调试                     ← 同"配置属性 > 调试"
```

> **提示**：**每个页面的"命令行"子页（或"所有选项"页）会实时显示当前配置对应的完整命令行**。想确认某个图形选项到底生成了什么开关，去那里看一眼最快——这是学习属性页最好的方法。

## 2. 配置属性 > 常规

| 字段 | 对应开关/变量 | 说明 |
|------|--------------|------|
| **输出目录** | `$(OutDir)` | 默认 `$(SolutionDir)$(Platform)\$(Configuration)\` |
| **中间目录** | `$(IntDir)` | `.obj`、`.pdb` 等中间产物 |
| **目标名称** | `$(TargetName)` | 默认等于项目名 |
| **目标扩展名** | `$(TargetExt)` | `.exe` / `.dll` / `.lib` |
| **配置类型** | `ConfigurationType` | **应用程序 / 动态库 / 静态库 / 生成文件** |
| **C++ 语言标准** | `/std:` | 见 2.5 节 |
| **Windows SDK 版本** | `WindowsTargetPlatformVersion` | 通常选"最新的已安装版本" |
| **平台工具集** | `PlatformToolset` | VS 2026 是 **`v145`** |
| **字符集** | `CharacterSet` | 使用 Unicode 字符集 / 使用多字节字符集 |

### 2.1 配置类型：改错了会得到奇怪的产物

| 配置类型 | 产物 | 何时选 |
|----------|------|--------|
| **应用程序 (.exe)** | 可执行文件 | 有 `main` 的项目 |
| **动态库 (.dll)** | `.dll` + 导入库 `.lib` | 运行时加载、跨语言调用（见 [[05-项目与解决方案管理|第 5 章]]） |
| **静态库 (.lib)** | `.lib` | 编译期链接进调用方 |
| **生成文件** | 不调用 MSVC | 交给 NMake 之类的自定义构建 |

> **注意**：**"没有 `main` 却选了应用程序"会报 `LNK1561: 必须定义入口点`**；反过来"有 `main` 却选了静态库"则会把 `main` 一起打进库里，链接时可能出现重复定义。

### 2.2 输出与中间目录

默认值依赖两个宏：

```text
$(SolutionDir)          → .sln 所在目录
$(Platform)             → x64 / Win32 / ARM64
$(Configuration)        → Debug / Release
$(ProjectDir)           → .vcxproj 所在目录
```

想统一把产物收到一个目录：

```text
输出目录：   $(SolutionDir)build\$(Platform)\$(Configuration)\
中间目录：   $(SolutionDir)build\intermediate\$(ProjectName)\$(Platform)\$(Configuration)\
```

> **实战场景**：中间目录**必须按项目分开**。如果多个项目共用同一个中间目录，`.obj` 与 `.pdb` 会互相覆盖，症状是"改了代码没生效""断点跳到别的文件"，极难排查。

### 2.3 字符集：Unicode 还是多字节

| 选项 | 效果 | 建议 |
|------|------|------|
| **使用 Unicode 字符集** | 定义 `_UNICODE` 与 `UNICODE`，`TCHAR` → `wchar_t`，`MessageBox` → `MessageBoxW` | ✅ 新项目一律选这个 |
| **使用多字节字符集** | 不定义上述宏，走 `char` 版本 API | 只在维护极老的代码时用 |

> **注意**：多字节字符集**早已被微软标记为弃用**。它和"中文乱码"关系密切，但**换字符集不是解决乱码的正确手段**——乱码的根因是源码编码与控制台代码页，见 [[13-常见问题与效率技巧#2. 中文乱码专题|第 13 章]]。

### 2.4 平台工具集与 Windows SDK

- **平台工具集**：`v145` 是 VS 2026 的默认值。改成 `v143` 就用 VS 2022 的编译器（需要已安装该工具集）。
- **Windows SDK 版本**：决定能用哪些 Windows API。选"最新的已安装版本"最省事；要兼容老系统时才需要降级。

### 2.5 C++ 语言标准：属性页选项 ↔ 编译器开关

| 属性页下拉项 | 编译器开关 | 说明 |
|--------------|-----------|------|
| ISO C++14 标准 | `/std:c++14` | 编译器的历史默认值 |
| ISO C++17 标准 | `/std:c++17` | |
| ISO C++20 标准 | `/std:c++20` | **VS 2026 新建项目的默认值**；隐含 `/permissive-` |
| 预览 - ISO C++23 标准 | `/std:c++23preview` | 只启用 C++23 范围内的特性 |
| 预览 - 最新 C++ 工作草案 | `/std:c++latest` | 含进行中的实验特性；隐含 `/permissive-` |

在 `.vcxproj` 里对应的属性是 `<LanguageStandard>`，常用取值：`stdcpp14`、`stdcpp17`、`stdcpp20`、`stdcpplatest`。

```xml
<ClCompile>
  <LanguageStandard>stdcpp20</LanguageStandard>
  <ConformanceMode>true</ConformanceMode>
</ClCompile>
```

> **注意**：**没有 `/std:c++26` 这个开关**。想用前沿特性只能挂 `/std:c++latest`，并接受"下个版本可能变"的风险。关于 C++23 与 `/std:c++23` 的时间线，见 [[01-VS2026概览与版本选择#4.3 C++23 与 C++26|第 1 章 4.3 节]]。

## 3. C/C++ > 常规

| 字段 | 开关 | 说明 |
|------|------|------|
| **附加包含目录** | `/I` | 头文件搜索路径 |
| **调试信息格式** | `/Zi` `/Z7` `/ZI` | 见 3.2 |
| **取消显示启动版权标志** | `/nologo` | 让输出干净一点 |
| **警告等级** | `/W0`–`/W4`、`/Wall` | 见 3.3 |
| **将警告视为错误** | `/WX` | 见 3.3 |
| **多处理器编译** | `/MP` | 见 3.4 |
| **使用 UTF-8 编码** | `/utf-8` | 见 3.5 |
| **SDLCheck** | `/sdl` | 额外的安全检查警告，建议开 |

### 3.1 附加包含目录

多个路径用**分号**分隔：

```text
D:\libs\fmt\include;$(ProjectDir)include;$(SolutionDir)third_party\eigen
```

> **提示**：`$(ProjectDir)` 这类宏在属性页里是**可用的**，用它写相对路径比写死绝对路径更适合团队协作。

### 3.2 调试信息格式

| 选项 | 开关 | 特点 |
|------|------|------|
| **程序数据库 (/Zi)** | `/Zi` | 调试信息写进 `.pdb`，**推荐**；支持"编辑并继续" |
| **C7 兼容 (/Z7)** | `/Z7` | 调试信息嵌进 `.obj`，文件大，但不用管 `.pdb` 丢失 |
| **用于"编辑并继续"的程序数据库 (/ZI)** | `/ZI` | 支持编辑并继续，但会禁用部分优化 |

> **注意**：VS 2026 中 **`/DEBUG:FASTLINK` 已被移除**，链接器调试信息请用 **`/DEBUG:FULL`**。老项目如果手工指定过 FASTLINK，升级后会直接报错。

### 3.3 警告等级与 `/WX`

| 等级 | 开关 | 含义 |
|------|------|------|
| 关闭所有警告 | `/W0` | ❌ 不建议 |
| 等级 1 | `/W1` | 严重警告 |
| 等级 2 | `/W2` | |
| 等级 3 | `/W3` | **MSVC 默认** |
| 等级 4 | `/W4` | ✅ 新项目建议 |
| 启用所有警告 | `/Wall` | 极其啰嗦，需要大量 `/wd` 屏蔽，谨慎使用 |

**将警告视为错误（`/WX`）**：把警告升级为错误。这是保证代码质量最有效的一招，但**迁移老项目时不要一上来就开**——先看 `/W4` 会刷出多少条，逐个处理完再开 `/WX`。

```cpp
// 只想在本地屏蔽某一条时，用代码级抑制（比全局 /wd 更精准）
#pragma warning(push)
#pragma warning(disable: 4996)
    std::strcpy(dst, src);   // 明知不安全但暂时保留
#pragma warning(pop)
```

### 3.4 多处理器编译（`/MP`）

`/MP` 让编译器**并行编译同一个项目里的多个 `.cpp`**。在 8 核机器上，十几个源文件的项目构建时间通常能减半。

**限制**：

- 与 `/Gm`（已弃用）不兼容；
- 与预编译头配合时需要注意；
- **只并行同一项目内的文件**——多项目并行由 MSBuild 的 `/m` 参数负责（**工具 > 选项 > 项目和解决方案 > 生成并运行 > 最大并行项目生成数**）。

### 3.5 使用 UTF-8 编码（`/utf-8`）

`/utf-8` 等价于同时指定：

```text
/source-charset:utf-8      源码文件按 UTF-8 解读
/execution-charset:utf-8   生成的窄字符串字面量用 UTF-8
```

**这是现代 C++ 项目处理中文最省事的方案**：源码存 UTF-8（不带 BOM 也行），加 `/utf-8`，代码里的中文字符串字面量就不会在编译期被按 GBK 误解。控制台输出乱码是另一层问题，见 [[13-常见问题与效率技巧#2. 中文乱码专题|第 13 章]]。

## 4. C/C++ > 优化

| 属性页选项 | 开关 | 含义 | 何时用 |
|-----------|------|------|--------|
| **已禁用** | `/Od` | 不做优化 | Debug |
| **最小化大小** | `/O1` | 体积优先 | 体积敏感的发布版 |
| **最大化速度** | `/O2` | 速度优先 | ✅ Release 默认 |
| **完全优化** | `/Ox` | 折中 | 较少用 |
| **自定义** | 逐项设置 | | 精细控制 |

细项：

| 细项 | 开关 | 说明 |
|------|------|------|
| **内联函数展开** | `/Ob0` `/Ob1` `/Ob2` | `/Ob2` 是 `/O2` 的默认 |
| **启用内部函数** | `/Oi` | 用内建指令替换 `memcpy` 之类 |
| **优选大小或速度** | `/Ot` `/Os` | 默认 `/Ot`（速度） |
| **启用纤维安全优化** | `/GT` | 使用纤程时开启 |
| **整个程序优化** | `/GL` | 跨编译单元优化，**必须配合链接器的 `/LTCG`** |

> **注意**：**`/GL` 与 `/LTCG` 必须成对出现**。只开 `/GL` 不开 `/LTCG`，链接器会给出警告并退化为普通链接，白折腾一场。Release 配置模板通常已经成对开好了。

> **实战场景**：`/O2` 会暴露未定义行为。代码在 Debug 下跑得好好的，Release 下崩溃或结果不对——先怀疑**未初始化变量、越界访问、有符号溢出**，而不是怀疑编译器。用 AddressSanitizer 复查，见 [[09-性能分析与诊断|第 9 章]]。

## 5. C/C++ > 预处理器

| 字段 | 开关 | 示例 |
|------|------|------|
| **预处理器定义** | `/D` | `WIN32;_DEBUG;_CONSOLE;MYLIB_EXPORTS` |
| **取消预处理器定义** | `/U` | 取消某个宏 |
| **忽略标准包含路径** | `/X` | 忽略 `INCLUDE` 环境变量 |
| **保留注释** | `/C` | 保留注释到预处理输出 |

**注意保留 `%(PreprocessorDefinitions)`**：

```xml
<PreprocessorDefinitions>MY_FEATURE=1;%(PreprocessorDefinitions)</PreprocessorDefinitions>
```

`%(...)` 是"继承已有的定义"。**漏掉它会把 Debug/Release 模板自带的 `_DEBUG`、`NDEBUG` 等宏全部覆盖掉**，导致 `assert` 行为异常——这是手改 `.vcxproj` 时最常见的错误。

## 6. C/C++ > 代码生成

### 6.1 运行库：`/MD` 还是 `/MT`

这是 C++ 在 Windows 上最重要的一条配置。

| 属性页选项 | 开关 | CRT 链接方式 | 部署要求 |
|-----------|------|-------------|----------|
| **多线程调试 DLL (/MDd)** | `/MDd` | 动态链接调试版 CRT | Debug 用 |
| **多线程 DLL (/MD)** | `/MD` | **动态**链接发行版 CRT | 目标机需装 **VC++ 可再发行程序包** |
| **多线程调试 (/MTd)** | `/MTd` | 静态链接调试版 CRT | Debug 用 |
| **多线程 (/MT)** | `/MT` | **静态**链接发行版 CRT | 免依赖，但体积大 |

| 维度 | `/MD` | `/MT` |
|------|-------|-------|
| 体积 | 小 | 大（每个 exe/dll 都带一份 CRT） |
| 部署 | 需要 `vc_redist` | 拷过去就能跑 |
| 跨 DLL 传 CRT 对象 | ✅ 可以 | ❌ 危险 |
| 多个模块共享堆 | ✅ 同一份堆 | ❌ 各自的堆 |
| 与第三方库混用 | 通常没问题 | **必须完全一致** |

> **注意（铁律）**：**同一个程序里的所有编译单元与所有静态库，必须使用同一种运行库选项。** 混用 `/MT` 与 `/MD` 会让同一个进程里出现**两份 CRT、两个堆**——在 A 模块里 `new`、在 B 模块里 `delete`，就是**堆损坏**，症状是随机崩溃且极难定位。
>
> 静态库混用通常会在链接期被 **`LNK2038`**（`RuntimeLibrary` 不匹配）拦下；但**通过 DLL 边界混用时链接器发现不了**，只能靠发布前的人工检查。

### 6.2 启用 C++ 异常

| 选项 | 开关 | 说明 |
|------|------|------|
| **是** | `/EHsc` | ✅ 推荐：只捕获 C++ 异常，假定 extern "C" 函数不抛 |
| **是，但有 extern "C" 函数** | `/EHs` | 假定 extern "C" 可能抛 |
| **是，但有 SEH 异常** | `/EHa` | 同时捕获结构化异常，会拖慢性能 |

> **注意**：`/EHsc` 不只是"打开异常"，它还告诉编译器**析构函数需要参与栈展开**。用 `/EHs` 或 `/EHa` 代替 `/EHsc` 可能带来性能损失，而完全不开异常会让 `try/catch` 报错。

### 6.3 其他代码生成选项

| 字段 | 开关 | 建议 |
|------|------|------|
| **启用运行时类型信息** | `/GR`（关闭为 `/GR-`） | 用 `dynamic_cast` / `typeid` 就必须开 |
| **启用函数级链接** | `/Gy` | ✅ 开，配合 `/OPT:REF` 能显著减小体积 |
| **缓冲区安全检查** | `/GS` | ✅ 开（默认开） |
| **控制流保护** | `/guard:cf` | ✅ 建议开，缓解劫持攻击 |
| **启用最小重新生成** | `/Gm` | ❌ 已弃用，别开 |
| **启用增强指令集** | `/arch:` | 见下 |

**`/arch:` 的取值与风险**：

| 选项 | 含义 | 风险 |
|------|------|------|
| `/arch:SSE2` | x86 默认 | 安全 |
| `/arch:AVX` | 使用 AVX | 老 CPU 会崩 |
| `/arch:AVX2` | 使用 AVX2 | **在不支持的机器上直接 `0xC000001D`（非法指令）** |
| `/arch:AVX512` | 使用 AVX-512 | 同上，且支持面更窄 |

> **实战场景**：为了那点性能开了 `/arch:AVX2`，结果在客户的旧机器上一启动就崩，报 `0xC000001D`。**要么用运行时分发（同一份代码编多个版本 + CPU 特性检测），要么老实留在 `/arch:SSE2`。** 详见 [[12-发布与部署|第 12 章]]。

## 7. C/C++ > 语言

| 字段 | 开关 | 说明 |
|------|------|------|
| **C++ 语言标准** | `/std:` | 见 2.5 节 |
| **符合模式** | `/permissive-` | 严格标准一致性，拒绝微软扩展 |
| **禁用特定警告** | `/wd####` | 如 `/wd4996` |
| **将警告视为错误** | `/WX` | |
| **C++ 异常** | `/EHsc` | 见 6.2 |
| **OpenMP 支持** | `/openmp` | 使用 `#pragma omp` |
| **C++ 模块支持** | 见下 | |

### 7.1 符合模式 `/permissive-`

`/permissive-` 关闭一堆历史遗留的宽松行为（两阶段名称查找、模板中的 `typename` 宽容处理等）。**`/std:c++20` 与 `/std:c++latest` 会自动启用它**，所以选了 C++20 之后，老代码可能突然报一堆错——这不是新标准的问题，而是**编译器终于按标准严格检查了**。

### 7.2 关于 `__cplusplus`

MSVC 为了兼容老代码，`__cplusplus` **默认永远是 `199711L`**。想让它反映真实标准，需要显式开启：

**C/C++ > 命令行 > 其他选项** 里加 `/Zc:__cplusplus`。

或者干脆用 `_MSVC_LANG` 判断（推荐）：

```cpp
#if _MSVC_LANG >= 202002L
    // C++20 及以上
#endif
```

### 7.3 C++ 模块

C++20 模块在 MSVC 上已可用，但需要显式开启。在属性页里把相关选项打开（或在命令行加 `/std:c++20 /experimental:module` 之类），并把模块接口单元（`.ixx`）的文件项类型设为"**C/C++ 编译器**"。模块的构建配置比传统头文件复杂，**团队项目里建议先用 CMake 统一管理**，见 [[10-CMake与vcpkg集成|第 10 章]]。

## 8. C/C++ > 高级

| 字段 | 开关 | 用途 |
|------|------|------|
| **强制包含文件** | `/FI` | 每个源文件隐式包含某头文件 |
| **编译为** | `/TC` `/TP` | 强制按 C 或 C++ 编译 |
| **禁用特定警告** | `/wd` | |
| **显示包含文件** | `/showIncludes` | 排查"这个头文件从哪来的" |
| **预编译头** | `/Yc` `/Yu` `/Fp` | 见第 12 节 |
| **调用约定** | `/Gd` `/Gr` `/Gz` | 一般不改 |

### 8.1 强制包含 `/FI`

```text
/FI"pch.h"
```

等价于在每个 `.cpp` 顶部自动写一行 `#include "pch.h"`。配合预编译头使用，或者用来统一注入版本宏。

### 8.2 显示包含文件 `/showIncludes`

排查头文件依赖的神器。开启后，**输出窗口**会列出每个源文件实际包含的全部头文件（带层级缩进）：

```text
1>注意: 包含文件:  D:\cpp\App\pch.h
1>注意: 包含文件:  C:\Program Files\...\include\vector
1>注意: 包含文件:  D:\cpp\App\config.h
```

配合第 9 章的 Build Insights，可以精确定位"哪个头文件拖慢了编译"。

## 9. 链接器

### 9.1 常规

| 字段 | 开关 | 说明 |
|------|------|------|
| **附加库目录** | `/LIBPATH` | `.lib` 搜索路径 |
| **启用增量链接** | `/INCREMENTAL` | Debug 默认开；Release 建议关 |
| **忽略导入库** | `/IGNORE` | |

### 9.2 输入

| 字段 | 开关 | 说明 |
|------|------|------|
| **附加依赖项** | 直接写 `.lib` 名 | 如 `fmt.lib;ws2_32.lib` |
| **忽略特定默认库** | `/NODEFAULTLIB` | 谨慎使用 |
| **强制符号引用** | `/INCLUDE` | 强制拉入某个符号（常用于静态库注册） |

> **提示**：**"附加库目录"负责去哪找，"附加依赖项"负责找什么**——两者要配套设置，只设一个必然报 `LNK2019` 或 `LNK1104`。

### 9.3 系统

| 字段 | 开关 | 说明 |
|------|------|------|
| **子系统** | `/SUBSYSTEM:CONSOLE` | 控制台程序：有黑窗口，入口 `main` |
| | `/SUBSYSTEM:WINDOWS` | GUI 程序：无黑窗口，入口 `WinMain` |
| **堆栈保留大小** | `/STACK` | 默认 1 MB；递归很深的算法需要加大 |

> **注意**：**子系统选错会导致 `LNK2019: 无法解析的外部符号 main`（或 `WinMain`）**。控制台程序误设成 WINDOWS，就会出现"找不到 `main`"这种看似荒谬的报错——因为链接器在找 `WinMain`。

### 9.4 优化

| 字段 | 开关 | 说明 |
|------|------|------|
| **链接时间代码生成** | `/LTCG` | **必须与 `/GL` 成对** |
| **引用** | `/OPT:REF` | 删除未引用代码，Release 默认开 |
| **启用 COMDAT 折叠** | `/OPT:ICF` | 合并相同函数，Release 默认开 |

### 9.5 高级

| 字段 | 开关 | 建议 |
|------|------|------|
| **入口点** | `/ENTRY` | 一般不用手改 |
| **随机基址** | `/DYNAMICBASE` | ✅ 保持开启（安全缓解） |
| **数据执行保护** | `/NXCOMPAT` | ✅ 保持开启 |
| **目标计算机** | `/MACHINE` | 通常自动 |

### 9.6 调试

| 字段 | 开关 | 说明 |
|------|------|------|
| **生成调试信息** | `/DEBUG` | 配合"生成完整程序数据库"= `/DEBUG:FULL` |
| **生成程序数据库文件** | `/PDB` | PDB 路径与文件名 |
| ~~生成快速链接调试信息~~ | ~~`/DEBUG:FASTLINK`~~ | **VS 2026 已移除**，老项目需改掉 |

## 10. 生成事件

三个入口，按执行时机排列：

```text
生成前事件  →  编译  →  链接前事件  →  链接  →  生成后事件
```

常用于：拷贝依赖 DLL 到输出目录、生成版本头文件、调用代码生成器。

**可用宏**：

| 宏 | 含义 |
|----|------|
| `$(SolutionDir)` | 解决方案目录（**含结尾反斜杠**） |
| `$(ProjectDir)` | 项目目录（含结尾反斜杠） |
| `$(ProjectName)` / `$(SolutionName)` | 名称 |
| `$(OutDir)` | 输出目录（含结尾反斜杠） |
| `$(IntDir)` | 中间目录 |
| `$(TargetPath)` | 输出文件的完整路径 |
| `$(TargetName)` / `$(TargetExt)` | 文件名与扩展名 |
| `$(Configuration)` / `$(Platform)` | 当前配置与平台 |

一个典型的生成后事件（把第三方 DLL 拷到输出目录）：

```bat
xcopy /Y /I "$(SolutionDir)third_party\bin\$(Platform)\*.dll" "$(OutDir)"
```

> **注意**：`$(SolutionDir)` 只在**通过解决方案构建**时才有定义。如果直接 `msbuild MyProject.vcxproj`（不经过 `.sln`），它是空的——生成事件会静默失败。稳妥写法是用 `$(ProjectDir)` 加相对路径。

## 11. 调试属性页

**配置属性 > 调试** 决定了按 `F5` 时发生什么：

| 字段 | 说明 |
|------|------|
| **命令** | 要启动的可执行文件（默认 `$(TargetPath)`） |
| **命令参数** | 传给程序的命令行参数 |
| **工作目录** | 程序的当前目录（**读相对路径文件时很关键**） |
| **环境** | 临时环境变量，如 `PATH=$(OutDir);%PATH%` |
| **调试器类型** | 自动 / 仅限本机 / 混合等 |
| **合并环境** | 是否继承系统环境变量 |

> **提示**：**VS 2026 也可以直接从工具栏设置命令行参数**，不必每次都进属性页。这一能力现在对 `.vcxproj`、CMake 与 Unreal 项目都可用，且不再依赖"使用 C++ 的游戏开发"工作负荷。

**注意**：这些设置存在 **`.vcxproj.user`** 里，是**本机**配置，不要提交到 Git。团队共用的参数应写进 `.vcxproj`。

> **实战场景**：程序在工作目录不对时读不到配置文件。把"工作目录"设成 `$(ProjectDir)`，并在代码里用相对路径 `"config/settings.ini"`，本地调试就稳定了。

## 12. 预编译头（PCH）实践

**目的**：把那些"又大又几乎不变"的头文件（`<vector>`、`<string>`、Windows SDK 头）**只解析一次**，后续编译直接复用，能显著加快构建。

**配置步骤**：

1. 建 `pch.h`，把常用头文件放进去；
2. 建 `pch.cpp`，内容只有一行 `#include "pch.h"`；
3. 选中 `pch.cpp` → **属性 > C/C++ > 预编译头 > 预编译头** 设为 **创建 (/Yc)**；
4. 选中其余所有 `.cpp` → 同一项设为 **使用 (/Yu)**；
5. 可选：在 **C/C++ > 高级 > 强制包含文件** 里填 `pch.h`。

**常见报错**：

| 报错 | 原因 | 处置 |
|------|------|------|
| `C1010: 查找预编译头时遇到意外的文件结尾` | 某个 `.cpp` 没包含 `pch.h` | 在文件首行加 `#include "pch.h"` |
| `C1853: 预编译头文件来自早期版本的编译器` | 工具集换了但 PCH 没重建 | **重新生成**解决方案 |
| `C1083: 无法打开预编译头文件` | `pch.cpp` 没设为"创建" | 检查第 3 步 |

> **注意**：`/Yc` 只能有**一个**文件。把它误设到多个 `.cpp` 上会报重复定义。

## 13. 多核编译与构建速度

按性价比排序：

| 手段 | 做法 | 收益 |
|------|------|------|
| **`/MP`** | C/C++ > 常规 > 多处理器编译 = 是 | 单项目内并行，收益最大 |
| **MSBuild 并行项目** | 工具 > 选项 > 项目和解决方案 > 最大并行项目生成数 | 多项目解决方案 |
| **预编译头** | 见第 12 节 | 大型项目显著 |
| **`/GL` + `/LTCG`** | Release | 提升运行性能，但**会拖慢链接** |
| **关闭增量链接** | Release 下 | 避免增量链接的额外开销 |
| **减少头文件依赖** | 前置声明、PIMPL | 治本 |
| **`/showIncludes` 或 Build Insights** | 找出"谁最慢" | 定位问题 |

> **提示**：MSVC 14.51 起启用了**调试信息裁剪**来减小 PDB 体积，大型项目的 `.pdb` 会明显变小。如果 PDB 曾经大到难以管理，升级工具集本身就有收益。

## 14. 配置的三种持久化方式

| 方式 | 载体 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **图形界面** | `.vcxproj` | 直观、即时生效 | 逐个项目改，易漏配置 | 单人、少量项目 |
| **属性表** | `.props` | 一处修改、多项目共享 | 需要理解导入顺序 | 团队统一规范 |
| **`Directory.Build.props`** | 目录级 XML | **自动应用**到该目录及子目录所有项目 | 隐式生效，新人容易"找不到配置在哪" | 整个仓库统一基线 |

`Directory.Build.props` 示例：

```xml
<Project>
  <PropertyGroup>
    <LanguageStandard>stdcpp20</LanguageStandard>
    <WarningLevel>Level4</WarningLevel>
    <MultiProcessorCompilation>true</MultiProcessorCompilation>
    <CharacterSet>Unicode</CharacterSet>
  </PropertyGroup>
  <ItemDefinitionGroup>
    <ClCompile>
      <AdditionalOptions>/utf-8 %(AdditionalOptions)</AdditionalOptions>
    </ClCompile>
  </ItemDefinitionGroup>
</Project>
```

> **注意**：`Directory.Build.props` 是**从项目目录向上查找**并自动导入的，**不需要在项目里写 `<Import>`**。好处是统一，坏处是"这个 `/W4` 到底是哪来的"——排查时记得往上看目录树。属性表的导入顺序见 [[05-项目与解决方案管理|第 5 章]]。

## 15. 从默认配置到生产配置：改动清单

| 配置项 | Debug | Release | 理由 |
|--------|-------|---------|------|
| 优化 | `/Od` | `/O2` | 调试要准，发布要快 |
| 调试信息 | `/Zi` | `/Zi`（保留 PDB 并归档） | 线上崩溃要靠它分析 |
| 运行库 | `/MDd` | `/MD` | 与可再发行包配套 |
| 警告等级 | `/W4` | `/W4` + **`/WX`** | 发布前零警告 |
| 多处理器编译 | `/MP` | `/MP` | 都受益 |
| 字符集 | Unicode | Unicode | 保持一致 |
| C++ 标准 | `/std:c++20` | `/std:c++20` | **两套必须一致**，否则行为不同 |
| `/GL` + `/LTCG` | 关 | 开 | 跨模块优化 |
| `/arch:` | SSE2 | SSE2（除非确定目标机支持） | 避免非法指令崩溃 |
| 增量链接 | 开 | 关 | 发布构建要干净 |
| 调试属性页参数 | 本地路径 | **清空** | 不要把本机路径带进发布 |
| `/utf-8` | 开 | 开 | 中文一致 |

> **注意**：**Debug 与 Release 的"语言标准"必须一致**。Debug 用 C++20、Release 用 C++17，会导致某些代码只在一种配置下能编译，或产生不同的重载决议——这是非常隐蔽的一类 bug。

## 小结

- **属性页改的是"当前配置 × 平台"**，改完记得切到 **所有配置** 或逐个检查——这是最高频的踩坑点。
- **C++ 语言标准**：新建项目默认 `/std:c++20`；没有 `/std:c++26`；`/std:c++20` 与 `/std:c++latest` 会隐含 `/permissive-`。
- **运行库 `/MD` 与 `/MT` 必须全局一致**，混用会导致堆损坏；DLL 边界上的混用链接器发现不了。
- **`/GL` 与 `/LTCG` 必须成对**；`/Gy` 配合 `/OPT:REF` 能减小体积。
- **`/utf-8`** 是现代项目处理中文源码的推荐做法。
- **`/arch:AVX2` 在旧 CPU 上会直接崩溃**（`0xC000001D`），非必要不要开。
- **子系统选错**会报"找不到 `main`"；**配置类型选错**会报"必须定义入口点"。
- **`/DEBUG:FASTLINK` 已在 VS 2026 移除**，用 `/DEBUG:FULL`。
- 改 `.vcxproj` 的 `PreprocessorDefinitions` 时，**别漏掉 `%(PreprocessorDefinitions)`**。
- 团队统一配置优先用 **`Directory.Build.props`** 或**属性表**，而不是逐个项目点属性页。

## 练习题

1. 打开一个控制台项目，把"配置"切成 **所有配置**，统一把语言标准设为 `/std:c++20`、警告等级设为 `/W4`；然后逐个配置切过去确认都生效了。
2. 分别在 `/std:c++14` 与 `/std:c++20` 下编译同一段使用了 C++17 结构化绑定的代码，记录两次报错信息，并解释为什么。
3. 把项目的运行库从 `/MD` 改成 `/MT`，用 `dumpbin /dependents` 对比改前改后的依赖列表，说明差异。
4. 故意把"子系统"从 `CONSOLE` 改成 `WINDOWS`，观察报错；再改回来。解释链接器在找什么。
5. 为一个含 10 个以上 `.cpp` 的项目配置预编译头，记录开启前后的构建耗时；再故意让一个文件漏掉 `#include "pch.h"`，记录报错码。
6. 用 `/showIncludes` 找出某个源文件包含的头文件总数，再指出其中最"重"的两个并说明理由。
7. 写一份 `Directory.Build.props`，为某目录下所有项目统一开启 `/W4`、`/MP`、`/utf-8`，并验证新建的项目自动继承了这些设置。
8. 用"命令行"子页（或"所有选项"页）抄下 Debug|x64 与 Release|x64 两份完整命令行，逐项对比差异并解释每一项的作用。
