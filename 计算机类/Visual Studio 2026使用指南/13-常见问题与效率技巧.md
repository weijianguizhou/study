# 13-常见问题与效率技巧

前面各章把 Visual Studio 的功能按模块讲了一遍，这一章换成问题导向：先把实际开发中最常撞上的报错做成速查表，再集中处理中文乱码、IntelliSense 与实际编译不一致、断点失效这类"配置型疑难"，最后收一整套效率技巧与快捷键总表。本章偏工具书性质，遇到问题直接翻到对应小节即可，不必从头读。

## 1. 编译与链接错误速查

### 1.1 错误号前缀对应哪个阶段

```text
        源码与项目文件
              │
              ▼
   ┌────────────────────────┐
   │ ① MSBuild (MSBxxxx)    │  解析 .vcxproj、工具集与 SDK、执行生成事件
   └───────────┬────────────┘
               ▼
   ┌────────────────────────┐
   │ ② 编译器 cl.exe (Cxxxx)│  预处理 → 语法 → 语义 → 代码生成 → .obj
   └───────────┬────────────┘
               ▼
   ┌────────────────────────┐
   │ ③ 链接器 link.exe      │  合并 .obj 与 .lib → .exe / .dll
   │    (LNKxxxx)           │
   └───────────┬────────────┘
               ▼
          可执行文件

   旁路：IntelliSense (Exxxx) 只在编辑器里做实时分析，不参与真实生成
```

| 前缀 | 来源 | 判断要点 |
| --- | --- | --- |
| `MSB` | MSBuild | 项目配置、工具集、SDK、生成事件的问题，还没轮到编译器 |
| `C` | 编译器 `cl.exe` | 语法、语义、头文件、预处理、代码生成 |
| `LNK` | 链接器 `link.exe` | 符号找不到或重复、库、入口点、位数冲突 |
| `E` | IntelliSense | 只影响编辑器的波浪线，**不一定**影响编译 |

### 1.2 编译器高频错误（`C` 系列）

| 错误号 | 提示信息要点 | 常见原因 | 解决方案 |
| --- | --- | --- | --- |
| `C2065` | 未声明的标识符 | 拼写错误、忘了 `#include`、少了 `std::` 限定、语言标准不够新 | 按提示里的标识符核对拼写与头文件；检查 **项目 > 属性 > C/C++ > 语言 > C++ 语言标准** |
| `C3861` | 找不到标识符 | 函数没声明、模板依赖名称少了 `this->` 或 `typename` | 补头文件或前置声明；模板中显式写 `this->member` |
| `C2143` | 语法错误：缺少 `;` | 上一行少分号、类定义后漏分号、宏展开后语法破损 | 看**上一行**；用 **C/C++ > 预处理器 > 预处理到文件** 观察宏展开结果 |
| `C1083` | 无法打开源文件 / 包含文件 | 头文件路径没配、大小写不符、文件不在磁盘上、SDK 未安装 | 在 **C/C++ > 常规 > 附加包含目录** 补齐路径，并确认配在"所有配置、所有平台" |
| `C1010` | 在查找预编译头时遇到意外的文件结尾 | 新增的 `.cpp` 忘了首行 `#include "pch.h"` | 补上包含，或对该文件设置 **C/C++ > 预编译头 > 预编译头 = 不使用预编译头** |
| `C4819` | 该文件包含不能在当前代码页（936）中表示的字符 | 源码为 UTF-8 无 BOM，编译器按系统 ANSI 代码页解析 | 另存为 UTF-8 with BOM，或加 `/utf-8`（见第 2 节） |
| `C4996` | 该函数或变量可能不安全，请考虑改用 `xxx_s` | 使用了被标记弃用的 CRT 函数（`strcpy`、`sprintf`、`localtime` 等） | 换用安全版本，或在 **C/C++ > 预处理器 > 预处理器定义** 加 `_CRT_SECURE_NO_WARNINGS` |
| `C2440` | 无法从 `X` 转换为 `Y` | 指针与整数混用、丢失 `const`、少了显式转换 | 补 `static_cast` 等显式转换，并回头检查类型设计 |
| `C2664` | 无法将参数 N 从 `X` 转换为 `Y` | 实参类型不匹配、`char*` 与 `wchar_t*` 混用、字符集设置不对 | 检查 **项目 > 属性 > 高级 > 字符集** 是否与代码一致 |
| `C2039` | `xxx` 不是 `yyy` 的成员 | 头文件版本不匹配、命名空间或类名写错 | 用 `F12` 转到定义核对真实成员列表 |
| `C2084` | 函数已有主体 | 同一函数被定义两次，通常是头文件里直接写了定义 | 改为 `inline`，或把定义移到 `.cpp` |
| `C2220` | 警告被视为错误——没有生成对象文件 | 项目开了 `/WX`，某些警告被升级为错误 | 先修触发它的警告（常见搭档是 `C4819`） |

### 1.3 链接器高频错误（`LNK` 系列）

| 错误号 | 提示信息要点 | 常见原因 | 解决方案 |
| --- | --- | --- | --- |
| `LNK2019` | 无法解析的外部符号 `xxx`，该符号在函数 `yyy` 中被引用 | 只声明未定义、`.cpp` 未加入项目、`.lib` 未加进附加依赖项、C/C++ 混用少了 `extern "C"`、模板实现放在了 `.cpp` | 按符号名反查定义；把 `.lib` 加到 **链接器 > 输入 > 附加依赖项**；确认库的位数与 CRT 设置一致 |
| `LNK2001` | 无法解析的外部符号（同族提示） | 同上，多见于静态成员变量未定义、虚函数表缺失 | 为静态成员补类外定义 |
| `LNK1120` | N 个无法解析的外部命令 | 只是上面两类错误的统计行 | 忽略它，去修具体的 `LNK2019` / `LNK2001` |
| `LNK2005` | `xxx` 已经在 `yyy.obj` 中定义 | 头文件里定义了非 `inline` 的全局函数或变量、用 `#include` 引入了 `.cpp`、两个库提供了同一符号 | 加 `inline` 或 `static`、把定义移到 `.cpp`、去掉重复包含；不到万不得已不要用 `/FORCE:MULTIPLE` |
| `LNK1169` | 找到一个或多个多重定义的符号 | 与 `LNK2005` 成对出现 | 处理掉 `LNK2005` 即可 |
| `LNK1104` | 无法打开文件 `xxx` | 库路径不对或库名拼错；**上一次的程序还在运行，exe 被占用**；文件被安全软件锁住 | 先结束残留进程再重新生成；核对 **链接器 > 输入 > 附加依赖项** 与库目录 |
| `LNK1561` | 必须定义入口点 | 没有 `main`/`wmain`/`WinMain`，或子系统类型与控制台/窗口程序不符 | 补入口函数，或改 **链接器 > 系统 > 子系统** |
| `LNK1112` | 模块计算机类型 `x64` 与目标计算机类型 `x86` 冲突 | 混入了位数不对的 `.lib` 或 `.obj` | 统一平台为 x64 或 x86，检查第三方库位数 |
| `LNK2038` | 检测到 `RuntimeLibrary` 的不匹配项：值 `MT_StaticRelease` 不匹配值 `MD_DynamicRelease` | 同一程序内混用 `/MT` 与 `/MD`，或 Debug 与 Release 混用 | 全工程与所有第三方库统一运行库设置（见第 12 章） |
| `LNK4098` | defaultlib `MSVCRT` 与其他库的使用冲突 | 显式链接了不同版本的 CRT 库 | 先统一运行库设置；仍冲突时再用 **链接器 > 输入 > 忽略特定默认库** |

### 1.4 MSBuild 与 IntelliSense 错误

| 错误号 | 提示信息要点 | 常见原因 | 解决方案 |
| --- | --- | --- | --- |
| `MSB8020` | 找不到 `vXXX` 的生成工具（平台工具集 = `vXXX`） | 项目指定的平台工具集本机没装（打开的是别人机器上的工程，或安装时没勾 MSVC 生成工具） | 用 **项目 > 重定解决方案目标** 切到已安装的工具集，或在 Visual Studio 安装程序里补装 |
| `MSB8036` | 找不到 Windows SDK 版本 `10.0.xxxxx.0` | 项目指定的 SDK 本机没有 | 在 **项目 > 属性 > 常规 > Windows SDK 版本** 改成本机已装的版本，或补装该 SDK |
| `MSB4019` | 找不到导入的项目 `xxx.props` / `xxx.targets` | 属性表被移动或删除、扩展未安装 | 检查 `.vcxproj` 里的 `<Import>` 路径，移除失效引用 |
| `MSB3073` | 命令 `xxx` 已退出，代码为 N | **生成前/后事件** 里的命令失败 | 看输出窗口里该命令自身的报错；路径含空格要加引号，用 `$(ProjectDir)` 等宏替代相对路径 |
| `MSB6006` | `xxx.exe` 已退出，代码为 N | 自定义生成步骤或工具进程返回非零 | 单独在命令行里跑一遍该命令，看真实输出 |
| `E0020` | 标识符 `xxx` 未定义 | IntelliSense 没看到声明：路径没配到当前配置、宏或语言标准不一致 | 见第 3 节的处理顺序 |
| `E1696` | 无法打开源文件 `xxx` | 包含路径只配在某个配置或平台，其他配置下 IntelliSense 找不到 | 改到"所有配置、所有平台"，再 **重新扫描解决方案** |
| `E0135` | 命名空间 `std` 没有成员 `xxx` | IntelliSense 使用的语言标准低于代码所需 | 统一 **C/C++ > 语言 > C++ 语言标准**，并重新扫描 |

### 1.5 排错的通用流程

1. **永远从第一条错误开始修**，之后的报错大多是它的连锁反应。
2. 分清两个窗口：**视图 > 错误列表**（`Ctrl+\, Ctrl+E`）只给摘要；完整命令行与上下文在 **输出** 窗口的"生成"页里。
3. 需要更多细节时，把 **工具 > 选项 > 项目和解决方案 > 生成并运行 > MSBuild 项目生成输出详细程度** 调成 **详细** 或 **诊断**，再重新生成。
4. 打开 **项目 > 属性 > C/C++ > 命令行** 与 **链接器 > 命令行**，把 IDE 里的配置与真实命令行对照，"我明明配了"的问题多半出在这里。
5. 改完配置仍报同样的错，执行 **生成 > 重新生成解决方案**；再不行就关掉 VS，删掉 `bin`、`obj` 与 `.vs` 后重来。

> **提示**：`LNK2019` 给出的"出错位置"往往是**引用处**而不是**定义缺失处**。真正要找的是提示里的符号名，用 `Ctrl+T` 全局搜索这个符号最快。

## 2. 中文乱码专题

### 2.1 四层编码，先分清错在哪一层

```text
   源码文件（磁盘字节）       ① 文件编码：UTF-8 / UTF-8 with BOM / GBK
        │
        ▼
   编译器读取                 ② 源字符集：由 BOM 或 /source-charset 决定
        │
        ▼
   字符串字面量（.obj 字节）  ③ 执行字符集：由 /execution-charset 或 /utf-8 决定
        │
        ▼
   运行时输出到控制台         ④ 控制台按"当前输出代码页"解释这些字节
        │
        ▼
   屏幕上的汉字
```

四层里任何一层不一致都会看到乱码。最常见的组合是：源码为 UTF-8 无 BOM（第①层），编译器按系统 ANSI 代码页 936 解析（第②层），字符串里的 UTF-8 字节又被送到 936 的控制台（第④层），两层皆错。

### 2.2 推荐做法与各开关的含义

| 做法 | 效果 | 适用场景 |
| --- | --- | --- |
| 源码保存为 **UTF-8 with BOM** | MSVC 依据 BOM 自动识别为 UTF-8，不依赖开关 | 想少配选项、以 Windows 为主的项目 |
| 源码 UTF-8 无 BOM + **`/utf-8`** | 源字符集与执行字符集都按 UTF-8 处理 | 团队协作、跨平台、Git 友好，**推荐** |
| `/source-charset:utf-8` | 只指定源字符集 | 源码是 UTF-8，但希望执行字符集保持 GBK |
| `/execution-charset:gbk` | 让窄字符串按 GBK 编码 | 需要与只认 GBK 的老代码或老接口对接 |
| 源码 GBK（936）+ 不加开关 | 靠系统 ANSI 代码页"碰巧能用" | 仅老项目临时兼容，新项目不要这么做 |

必须记住的四点：

- **BOM 优先于 `/source-charset`**：文件带 BOM 时编译器按 BOM 判断编码，该开关对它不起作用。
- **`/utf-8` 是组合开关**：等价于同时指定 `/source-charset:utf-8` 与 `/execution-charset:utf-8`。
- 代码页写法上，`/source-charset:.936` 以点号开头的数字表示代码页，`utf-8` 这类名字直接书写。
- `/execution-charset` 只影响**窄字符串与字符字面量**；`u8"..."` 在 C++17 是 `const char[]`，C++20 起是 `const char8_t[]`。想只改单个文件的执行字符集，可在文件开头写 `#pragma execution_character_set("utf-8")`，但它修不了第①层的文件编码问题。

### 2.3 控制台输出中文的三种方案

**方案 A：全程 UTF-8（推荐）**。编译时加 `/utf-8`，程序启动时把控制台代码页切成 UTF-8：`SetConsoleOutputCP(CP_UTF8)` 管输出，`SetConsoleCP(CP_UTF8)` 管输入。批处理里先执行 `chcp 65001` 效果类似，但那是用户侧动作，程序自己设置才可靠。

**方案 B：保持 GBK（936）**。源码按 GBK 保存，或用 `/source-charset:utf-8 /execution-charset:gbk`，窄字符串里就是 GBK 字节，而中文 Windows 控制台默认输出代码页正是 936，不写任何代码即可正常显示。缺点是跨平台差、换区域设置就可能翻车。

**方案 C：宽字符 + 区域设置**。输出宽字符前调用 `setlocale(LC_ALL, "")`（跟随系统区域）或 `setlocale(LC_ALL, "zh-CN")`，再用 `std::wcout`。两个坑：其一，`setlocale` 不会改变控制台代码页，若同时又调了 `SetConsoleOutputCP(CP_UTF8)`，宽字符流仍按区域设置转换，可能出现双重转换的乱码；其二，不要让 `std::cout` 与 `std::wcout` 交替混用，窄宽流方向混用会导致输出错序甚至丢失。要在 UTF-8 控制台输出宽字符串，最稳的做法是先用 `WideCharToMultiByte(CP_UTF8, ...)` 转成 UTF-8 的 `std::string`，再交给 `std::cout`。

> **注意**：UCRT 也支持 UTF-8 形式的区域名，但它依赖较新的 Windows 系统组件。目标机版本偏老时不要依赖这一条，直接用方案 A。

### 2.4 一个"中文输出正确"的完整示例

```cpp
// main.cpp —— 保存为 UTF-8 with BOM，或使用 /utf-8 编译
#include <windows.h>
#include <iostream>

int main() {
    // ① 让控制台按 UTF-8 解释输出字节与输入字节
    SetConsoleOutputCP(CP_UTF8);
    SetConsoleCP(CP_UTF8);

    // ② 执行字符集为 UTF-8 时，窄字符串里存的就是 UTF-8 字节
    std::cout << "你好，世界！\n";
    std::cout << "中文注释与中文输出都不会乱码。\n";

    // ③ 打印当前输出代码页，正常应为 65001
    std::cout << "当前输出代码页：" << GetConsoleOutputCP() << "\n";
    return 0;
}
```

```bat
:: 手动编译时的等价命令行
cl /utf-8 /EHsc /W4 /MD main.cpp /link /SUBSYSTEM:CONSOLE
```

工程级的做法是在 `.vcxproj` 或属性表里给 **C/C++ > 命令行 > 其他选项** 统一加上 `/utf-8`，再在仓库根放一个 `.editorconfig` 并把 `charset` 设为 `utf-8-bom`，编辑器与 IDE 保存新文件时就会带上 BOM，从源头少踩一次编码的坑。

## 3. IntelliSense 与实际编译不一致

### 3.1 典型症状与原因

| 症状 | 可能原因 |
| --- | --- |
| 满屏红色波浪线，但生成成功 | IntelliSense 数据库过期，或它的语言标准、宏定义与真实编译不一致 |
| 编辑器不报错，一生成就 `C1083`/`C2065` | 包含路径或宏只配在某一个配置下，IntelliSense 恰好用的是能通过的那个 |
| 头文件上有绿色波浪线并报 `E1696` | `附加包含目录` 里的目录不存在，或没配到"所有配置、所有平台" |
| 成员列表缺项、`std::` 补全不全 | IntelliSense 的头文件搜索路径不完整，或语言标准偏低 |
| 明明存在的文件搜不到 | 文件只在磁盘上，没被加入项目，而 IntelliSense 按项目文件扫描 |

### 3.2 按顺序修复

1. **先确认真实编译结果**：按 `Ctrl+Shift+B` 生成一次，看 **输出** 窗口。编译器的 `C` 系列错误才是唯一真相，`E` 系列仅供参考。
2. **把包含路径配到"所有配置、所有平台"**：在 **项目 > 属性 > C/C++ > 常规 > 附加包含目录** 中，把左上角配置下拉切到 **所有配置**、平台切到 **所有平台**，再编辑。
3. **重新扫描**：在解决方案资源管理器中右键项目，选择 **重新扫描解决方案**。
4. **清掉缓存**：关闭 Visual Studio，删除解决方案目录下的隐藏文件夹 `.vs`，必要时一并删除 `ipch`、`*.VC.db` 等浏览数据库，再重新打开。
5. **对齐语言标准、宏与文件归属**：确认 **C/C++ > 语言 > C++ 语言标准** 与 **C/C++ > 预处理器 > 预处理器定义** 和命令行一致，并确认相关文件确实挂在项目节点下（从别的目录拖进来的文件常常只存在于磁盘）。
6. **CMake 工程**：用 **项目 > 删除缓存并重新配置**，必要时删掉 `out\build` 后重新打开。

> **实战场景**：同事把 `附加包含目录` 只加在了 Debug|x64 下，Release 一生成就 `C1083`，而他在编辑器里怎么看都正常——因为 IntelliSense 用的正是 Debug 配置。把下拉切成"所有配置、所有平台"重新添加后问题消失。

## 4. 路径与工程习惯

### 4.1 中文与空格路径引发的怪问题

- **空格**：生成事件、自定义生成步骤、外部工具的命令行若未给路径加引号，会被拆成多个参数，报出 `MSB3073` 这类看不出原因的错误。
- **中文**：部分老工具与第三方脚本按 ANSI 代码页处理路径，遇到中文目录会找不到文件，或打出乱码路径让人误判。
- **长路径**：路径总长超过 260 字符时部分工具会失败。缩短目录层级，或在系统上启用长路径支持（Windows 10 1607 起有对应的组策略与 `LongPathsEnabled` 注册表项）。
- **中文用户名**：`%USERPROFILE%` 含中文时，某些工具生成的临时路径同样会出问题，属同一类故障。

### 4.2 建议的目录规范

```text
D:\dev\                        ← 盘符浅、全英文、无空格
├── MyApp\                     ← 仓库根目录
│   ├── MyApp.sln
│   ├── src\                   ← 源码
│   ├── include\               ← 对外头文件
│   ├── third_party\           ← 第三方库（头文件 + lib + dll）
│   ├── resources\             ← 图标、图片、配置模板
│   └── build\                 ← 生成目录（x64\Debug、x64\Release 都在这里）
```

- 在 **项目 > 属性 > 常规** 里把 **输出目录** 与 **中间目录** 集中到 `build\$(Platform)\$(Configuration)\`，源码目录保持干净。
- 把共享设置（包含目录、警告等级、`/utf-8` 等）做成 `.props` 属性表，通过 **视图 > 属性管理器** 添加，避免逐个项目手工配置。
- `.vcxproj.user` 属于个人设置，不要提交。

## 5. 调试符号与断点失效

| 现象 | 原因 |
| --- | --- |
| 断点是**空心圆圈**，悬停提示"当前不会命中断点。尚未为该文档加载任何符号" | PDB 未加载，或 PDB 与二进制不是同一次生成的结果 |
| 提示"没有可执行代码与此行关联" | 该行被优化掉、被内联，或本身就是声明、注释、空行 |
| 断点能命中，但行号对不上、变量显示"已优化掉" | `/O2`、`/Oy` 等优化导致代码与源码行号错位 |
| 进不了系统库或第三方库源码 | "仅我的代码"跳过了非用户代码 |
| 附加到进程后断点全部失效，或换台机器打开就失效 | 附加的进程不是当前生成的 exe（旧进程仍在运行）；或源码路径与 PDB 中记录的不一致 |

按顺序修复：

1. 确认当前是 Debug 配置；若必须在 Release 下调，至少加 `/Zi`，并在 **链接器 > 调试 > 生成调试信息** 选择 **是 (/DEBUG)**。
2. 执行 **生成 > 重新生成解决方案**，保证 PDB 与 exe 同源——手工拷贝过 exe 却没带 PDB 是最常见的原因。
3. 打开 **调试 > 窗口 > 模块**（`Ctrl+Alt+U`）查看目标模块的符号状态，显示"未加载"时右键加载符号，并检查 **工具 > 选项 > 调试 > 符号** 的符号位置。
4. 取消 **工具 > 选项 > 调试 > 常规 > 启用"仅我的代码"**，即可单步进入系统或库代码；同时确认 **项目 > 属性 > 调试 > 调试器类型** 是 **自动** 或 **仅限本机**。
5. 优化引起的跳变无法消除时，在该行临时插入 `__debugbreak()` 强制中断；需要观察被优化掉的变量时，把 **C/C++ > 优化 > 优化** 临时设为 **已禁用 (/Od)** 复现问题。

> **注意**：Debug 配置里 **C/C++ > 代码生成 > 基本运行时检查** 默认是 **两者 (/RTC1)**，它要求关闭优化，二者配套。不要在同一配置里既开 `/O2` 又指望 `/RTC1` 生效。

## 6. 效率技巧集

### 6.1 编辑与代码

- **多光标与框选**：按住 `Ctrl+Alt` 点击可在多处插入光标，批量改名、批量加前缀特别顺手；按住 `Alt` 拖动鼠标则是框选（列选择），也可用 `Shift+Alt` 配方向键。
- **复制与移动行**：`Ctrl+E, V` 复制当前行（官方文档绑定；`Ctrl+D` 在不同上下文里可能被"查找"组合框占用）；`Alt+↑` / `Alt+↓` 上下移动行；`Ctrl+L` 剪切整行。
- **格式化与注释**：`Ctrl+K, Ctrl+D` 格式化文档，`Ctrl+K, Ctrl+F` 格式化选区；`Ctrl+K, Ctrl+C` 注释、`Ctrl+K, Ctrl+U` 取消注释，较新版本中 `Ctrl+/` 也能切换行注释。
- **剪贴板环**：`Ctrl+Shift+V` 循环粘贴前几次复制的内容，误覆盖的内容还能捞回来。
- **快速操作与结构化选择**：`Ctrl+.` 打开灯泡菜单，补头文件、加 `override`、生成定义都在这里；`Shift+Alt+=` 与 `Shift+Alt+-` 可按语法结构扩展与收缩选择。

### 6.2 导航

- **`Ctrl+T` / `Ctrl+,`**：转到全部 / 导航到，模糊搜索文件、类型、成员、符号，是最高频的导航方式。
- **`F12` / `Alt+F12`**：转到定义 / 速览定义（不离开当前文件，按 `Shift+Esc` 切回编辑器）。
- **`Ctrl+K, Ctrl+O`**：在头文件与实现文件之间来回切换，C++ 开发必备；`Ctrl+Alt+↑` 可跳到当前代码块的外层。
- **`Ctrl+-` / `Ctrl+Shift+-`**：在浏览历史中后退与前进。
- **书签**：`Ctrl+K, Ctrl+K` 打书签，`Ctrl+K, Ctrl+N` 跳到下一个，`Ctrl+K, Ctrl+W` 打开书签窗口看全貌。
- **`Ctrl+;`**：把焦点送到解决方案资源管理器的搜索框，找文件不用鼠标。

### 6.3 任务列表、代码片段与环境管理

TODO 注释会自动汇总进任务列表，不容易漏：

```cpp
// TODO: 补充参数校验
// HACK: 绕开上游库的越界问题，等对方修复
```

用 **视图 > 任务列表**（`Ctrl+\, Ctrl+T`）查看，双击跳到对应代码行；标记关键字可在 **工具 > 选项 > 环境 > 任务列表** 里增删。代码片段用 `Ctrl+K, Ctrl+X` 插入，常用的有 `#if`、`for`、`switch`、`class`、`ctor`、`try` 等；自定义片段用 **工具 > 代码片段管理器**（`Ctrl+K, Ctrl+B`）管理，"我的代码片段"目录下的 `.snippet` 就是普通 XML，改起来很容易。

环境层面的三件事值得花十分钟做一次：

- **自定义快捷键**：**工具 > 选项 > 环境 > 键盘** 里按命令名搜索（如 `Edit.FormatDocument`）后指派组合键。
- **导出与导入设置**：**工具 > 导入和导出设置向导** 可只导出"键盘""字体和颜色""窗口布局"等某一类设置，换机器几分钟恢复环境。
- **保存窗口布局**：把工具窗口摆顺手后用 **窗口 > 保存窗口布局** 存下来，编码布局与调试布局分别保存，需要时一键切换。

## 小结

- 先看错误号前缀：`MSB` 是项目与工具集、`C` 是编译器、`LNK` 是链接器、`E` 只是 IntelliSense；永远从第一条错误开始修。
- `LNK2019` 找定义与库，`LNK2005` 查头文件里的非 `inline` 定义与重复包含，`LNK1104` 先想到"程序还在运行导致 exe 被占用"。
- 中文乱码要分清源码编码、源字符集、执行字符集、控制台代码页四层，推荐"UTF-8 with BOM 或 `/utf-8`"配合 `SetConsoleOutputCP(CP_UTF8)`。
- IntelliSense 与编译不一致时依次做：确认真实编译结果、把包含路径配到"所有配置、所有平台"、重新扫描解决方案、删除 `.vs`。
- 工程路径坚持全英文、无空格、层级浅；`.vs`、`bin`、`obj` 一律进 `.gitignore`。
- 断点空心先查 PDB 与配置，其次查"仅我的代码"与调试器类型，最后才怀疑优化。
- 效率提升集中在四个动作：`Ctrl+T` 导航、`Ctrl+Alt+点击` 多光标、`Ctrl+K, Ctrl+D` 格式化、用书签与任务列表管住待办。

## 练习题

1. 故意制造一次 `LNK2019`（声明了函数却不实现），用错误列表与 `Ctrl+T` 定位并修复，记录提示信息里的关键字段。
2. 在头文件里定义一个非 `inline` 的全局函数，被两个 `.cpp` 包含，复现 `LNK2005` 与 `LNK1169`，然后给出两种不同的修复方式。
3. 把一个含中文注释的 GBK 源码在不加 `/utf-8` 的情况下编译，观察 `C4819`，再分别用"另存为 UTF-8 with BOM"和 `/utf-8` 修好，比较两种做法在代码页处理上的差异。
4. 写一个输出中文的控制台程序，分别在 `chcp 936` 与 `chcp 65001` 下运行，解释结果不同的原因，再改用 `SetConsoleOutputCP(CP_UTF8)` 让程序自己保证正确。
5. 把 `附加包含目录` 只配在 Debug 配置下，制造 IntelliSense 与实际编译不一致，然后按"所有配置 + 重新扫描 + 删除 `.vs`"的顺序修好。
6. 用 **工具 > 选项 > 环境 > 键盘** 给"设置文档格式"指派一个自定义组合键，再用 **工具 > 导入和导出设置向导** 把键盘设置导出为 `.vssettings` 文件。
