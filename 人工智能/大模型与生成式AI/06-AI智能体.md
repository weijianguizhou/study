# AI 智能体

> 单次问答的 LLM 是"会说话的人"；**AI 智能体（Agent）**是"会干活的人"——它能感知任务、制定计划、调用工具、检查结果、反复迭代。Agent = **LLM 大脑 + 规划 + 工具 + 记忆**。本篇从范式、工具调用、记忆、多智能体到工程实战完整展开。

## 1. 什么是 Agent

### 1.1 定义

一个 Agent 在循环中工作：读入状态 → 决策 → 执行动作 → 观察结果 → 再决策，直到任务完成。

$$
\text{Agent: } \underbrace{\text{LLM}}_{\text{决策/推理}} + \underbrace{\text{Planner}}_{\text{任务分解}} + \underbrace{\text{Tools}}_{\text{行动能力}} + \underbrace{\text{Memory}}_{\text{短期/长期}}
$$

### 1.2 与普通 LLM 调用的区别

| 维度 | 普通 LLM 调用 | Agent |
|------|--------------|-------|
| 输出 | 一次回答 | 多步行动序列 |
| 外部能力 | 无（只能写文本） | 可调用工具、执行代码、访问系统 |
| 状态 | 无 | 有目标、有进度、有中间结果 |
| 失败处理 | 重新问 | 观察结果、自我修正、重试 |
| 主动性 | 被动 | 可发起子任务、追问信息 |

## 2. Agent 范式

### 2.1 ReAct（推理 + 行动交替）

ReAct（Yao et al., 2022）把"思考（Reason）"与"行动（Act）"交错：模型逐步输出 `Thought → Action → Observation`，观察来自工具的真实反馈，再继续思考。见 [[02-提示工程|提示工程]] 3.3。

```
Thought: 用户想知道北京今天天气，我需要调用天气工具。
Action: weather_search(城市="北京")
Observation: 晴，27°C
Thought: 得到天气结果，可以回答了。
Action: finish(回答="北京今天晴，27°C")
```

**关键价值**：推理轨迹 + 真实反馈形成闭环，减少幻觉（行动失败能观察并纠正）。

### 2.2 Plan-and-Execute（先规划后执行）

不逐小步想，而是先生成完整计划，再逐项执行：

```
Plan:
  1. 收集用户需求文档
  2. 用分析工具统计销售数据
  3. 生成报告
执行第 1 步 → 观察 → 更新计划...
```

适合：任务步骤明确、可离线规划的场景；比 ReAct 省 token，但应对计划外情况能力弱。

### 2.3 Reflexion（反思）

在 ReAct 基础上增加**自我评估**：任务失败时让 LLM 生成"反思总结"，写回记忆，下一轮避免同样的错误：

```
执行失败：搜索结果为空。
反思：可能关键词太宽泛，下次应补充同义词并缩小时间范围。
```

适合：代码修复、游戏、重复性任务。

### 2.4 范式对比

| 范式 | 规划方式 | 优点 | 缺点 | 适用 |
|------|----------|------|------|------|
| ReAct | 逐小步 | 灵活、可纠错 | token 消耗大 | 大多数任务 |
| Plan-and-Execute | 一次性计划 | 省 token、步骤清晰 | 应变差 | 流程化任务 |
| Reflexion | 经验复盘 | 持续改进 | 需多次尝试 | 迭代型任务 |

## 3. 工具调用（Function Calling）

### 3.1 原理

LLM 本身不能执行代码，但它可以被"教会"输出一个结构化的函数调用请求，由宿主程序执行，把结果喂回模型：

```
用户: 上海明天会下雨吗？
模型: tools_calls: [{name: "get_weather", arguments: {city: "上海", date: "明天"}}]
宿主: 调用 API，返回 {"condition": "rain", "temp": 22}
模型: 会下雨，气温 22°C，记得带伞。
```

**Function Calling 的机制**：把工具 schema 随 system 消息一起给模型，模型在生成完回复之前输出一个专门的 `tool_calls` 对象。它本质是**结构化输出 + 多轮对话循环**。

### 3.2 Toolformer：让模型自己学会用工具

Toolformer（2023）通过"示例挖掘 + 采样打分"自动生成"调用工具"的训练数据：在文本中插入工具调用位置，如果调用后的结果能降低文本损失，就保留这条数据训练。思想：**把工具调用变成模型能力**，而不是宿主程序强加。

### 3.3 工具设计要点

- **工具数量**：一次暴露 5–15 个为宜，过多降低选择准确率；
- **命名**：动词开头、语义清晰；
- **参数 schema**：用 JSON Schema 精确描述（类型、必填、枚举、描述）；
- **错误返回**：工具失败返回可读错误信息，模型才能自我修正；
- **安全**：危险工具（删库、转账）加确认机制。

## 4. 记忆系统

### 4.1 两层记忆

| 记忆类型 | 载体 | 特点 | 用途 |
|----------|------|------|------|
| 短期记忆（工作记忆） | 上下文窗口 | 快、有容量上限 | 当前任务、中间结果 |
| 长期记忆 | 向量库/数据库 | 持久、需检索 | 跨会话经验、知识库 |

### 4.2 长期记忆实现

复用 [[04-RAG检索增强生成|RAG]] 的检索能力：

```
对话历史/经验 → 切片 → 嵌入 → 向量库
新会话开始时 → 检索相关记忆 → 注入 system prompt
```

### 4.3 上下文管理

长会话中 token 会撑爆上下文，常用策略：

- **摘要压缩**：定期把旧对话摘要成几行；
- **滑动窗口**：只保留最近 N 条；
- **分层存储**：近期全量 + 远期摘要/检索。

## 5. 多智能体协作

### 5.1 为什么需要多 Agent

单个 Agent 上下文与角色有限。多 Agent 让**分工 + 批判**成为可能：一个写、一个审、一个执行。

### 5.2 代表框架

| 框架 | 组织方式 | 特点 |
|------|----------|------|
| AutoGen | 对话式编排 | 可指定"说话顺序"、支持人机混合 |
| MetaGPT | 软件公司流程 | 角色 = 产品经理/架构师/工程师/QA，输出标准化文档 |
| CrewAI | 角色+任务 | 声明式定义 agents 与 tasks |
| LangGraph | 图状态机 | 显式控制 Agent 状态转移，生产友好 |

### 5.3 协作模式

- **主从模式**：一个 Orchestrator 分派任务给 Worker；
- **辩论模式**：多个 Agent 互相批判，收敛到一致答案；
- **流水线模式**：上游输出是下游输入（如 MetaGPT）；
- **群体智能**：大量 Agent 并行探索，投票/聚类选优。

### 5.4 代价

多 Agent 的调用次数与 token 消耗线性放大，且**错误会沿链条传播**（一个 Agent 的幻觉污染下游）。控制层级、限制轮次、加质量闸门（验证器）是工程必需。

## 6. 与经典自动规划的联系

经典 AI 的 [[../经典AI教程/04-逻辑推理与自动规划|自动规划]]（STRIPS）用**状态-行动-目标**描述问题，用搜索找行动序列。Agent 与其一脉相承：

| 维度 | 经典规划（STRIPS/POP） | LLM Agent |
|------|------------------------|-----------|
| 问题表示 | 形式化（谓词、状态转移） | 自然语言 |
| 规划生成 | 确定性搜索（最优/完备） | 概率生成（灵活不可靠） |
| 执行反馈 | 严格状态更新 | 自然语言观察 |
| 可验证性 | 可证明最优 | 难以证明 |
| 常识/泛化 | 无 | 强 |

**融合趋势**：Agent 的规划器可用符号求解器/代码（确定性），LLM 负责语义理解与常识（灵活性）——神经符号混合。经典 STRIPS 的"目标分解、前向搜索、回溯"思想，在现代 Agent 的 Plan-and-Execute 与 ReAct 中依然可见。

## 7. 经典案例

| 产品 | 形态 | 亮点 |
|------|------|------|
| AutoGPT（2023） | 实验性通用 Agent | 让"自主循环"概念破圈，但稳定性差 |
| Manus | 通用任务 Agent | 云端异步执行、交付产物 |
| Devin / Cursor | 代码智能体 | 写代码、跑测试、修 bug 的闭环 |
| Deep Research（OpenAI/Claude） | 研究 Agent | 多路检索 + 推理生成报告 |

代码智能体为何最有价值：**代码是精确的、可执行的、可验证的**——Agent 的执行结果可以立即被编译器/测试反馈，天然闭环。

## 8. Python 实战：Function Calling 实现一个天气/计算 Agent

用 OpenAI 兼容接口，做一个能查天气、做计算的助手。

```python
# pip install openai
from openai import OpenAI
import json, datetime

client = OpenAI(base_url="http://localhost:8000/v1", api_key="sk-xxx")

# 1. 声明两个工具
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名"},
                    "date": {"type": "string", "description": "日期, 默认今天"},
                },
                "required": ["city"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "calculator",
            "description": "执行四则运算, 如 '3*4+2'",
            "parameters": {
                "type": "object",
                "properties": {"expr": {"type": "string", "description": "数学表达式"}},
                "required": ["expr"],
            },
        },
    },
]

# 2. 工具的真实实现
def get_weather(city: str, date: str = ""):
    # 真实项目这里调天气 API
    return json.dumps({"city": city, "condition": "晴", "temp": 27, "date": date or "今天"})

def calculator(expr: str):
    return json.dumps({"expr": expr, "result": eval(expr)})  # 注意: eval 仅用于演示

TOOL_IMPL = {"get_weather": get_weather, "calculator": calculator}

# 3. Agent 主循环
def run_agent(question: str, max_turns: int = 5):
    messages = [{"role": "user", "content": question}]
    for _ in range(max_turns):
        resp = client.chat.completions.create(
            model="Qwen/Qwen2.5-7B-Instruct",
            messages=messages,
            tools=TOOLS,
            tool_choice="auto",
        )
        msg = resp.choices[0].message
        messages.append(msg)

        # 模型要求调用工具？
        if msg.tool_calls:
            for tc in msg.tool_calls:
                fn = tc.function.name
                args = json.loads(tc.function.arguments)
                print(f"[调用工具] {fn}({args})")
                result = TOOL_IMPL[fn](**args)      # 执行工具
                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": result,               # 把结果喂回模型
                })
            continue
        # 没有工具调用 → 最终回答
        return msg.content
    return "达到最大轮数，任务未完成"

print(run_agent("北京明天天气如何？顺便算一下 (28-15)*3 等于多少。"))
```

```
运行示例输出:
[调用工具] get_weather({'city': '北京', 'date': '明天'})
[调用工具] calculator({'expr': '(28-15)*3'})
北京明天晴，27°C。算式 (28-15)*3 的结果是 39。
```

**Agent 循环的三件套**（`messages` 结构）：模型输出 `assistant.tool_calls` → 宿主执行工具 → 追加 `role: "tool"` 结果 → 模型继续。这个循环加上"记忆、反思、规划"就构成完整 Agent。

## 9. 挑战与工程实践

### 9.1 挑战

| 挑战 | 表现 | 对策 |
|------|------|------|
| 安全 | 工具被滥用、prompt 注入 | 白名单工具、确认机制、沙箱 |
| 成本 | 多轮循环 token 爆炸 | 计划先行、控制轮次、缓存 |
| 错误传播 | 一步错步步错 | 反思、验证器、检查点 |
| 不可靠 | 同任务结果不稳定 | 多次采样 + 投票、确定性工具兜底 |
| 长任务漂移 | 执行到一半忘了目标 | 显式目标记忆、checkpoint 恢复 |

### 9.2 工程最佳实践

1. **能写代码就用代码**：精确计算交给 `calculator`/执行器，不让 LLM 心算；
2. **先验证再执行**：危险操作双重确认；
3. **工具错误可读**：返回结构化错误供模型修正；
4. **限制自由度**：不是轮次越多越好，给最大轮次与预算；
5. **可观测性**：记录每一步 Thought/Action/Observation 供复盘；
6. **人机协同**：关键节点交人确认（human-in-the-loop）。

## 10. 评估 Agent 系统

Agent 是多步交互系统，评估不能只看最终答案，要看"过程质量"与"任务完成度"。

### 10.1 评估维度

| 维度 | 指标 | 说明 |
|------|------|------|
| 任务完成度 | 成功率、完成率 | 最终目标是否达成 |
| 效率 | 轮次、token 数、工具调用数 | 越省越好 |
| 鲁棒性 | 同任务多次执行的稳定性 | 方差小为上 |
| 安全性 | 越权操作、敏感数据泄露 | 红队测试 |
| 轨迹质量 | 是否合理规划、及时纠错 | 人工抽审 |

### 10.2 评估方法

- **Golden 任务集**：准备 20–50 个有确定答案的任务，自动判成功；
- **轨迹回放**：记录 Thought/Action/Observation 供人工分析失败原因；
- **回归测试**：每次改 prompt/工具后重跑 golden 集；
- **沙箱压测**：在隔离环境跑危险动作，验证安全边界。

> Agent 工程的最大陷阱：**demo 能跑通 ≠ 系统稳定**。多轮、多工具、长任务的错误率会指数累积，务必用评估集守住质量下限。
