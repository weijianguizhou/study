# 推理与部署

> 训练教会模型"知识"，推理让知识"变现"。推理与部署关注：**在有限显存/预算下，把模型跑得快、跑得省、服务化**。核心四件套：量化、KV Cache、推理引擎、服务化协议。

## 1. 推理 vs 训练

### 1.1 根本区别

| 维度 | 训练 | 推理 |
|------|------|------|
| 目标 | 更新权重（梯度下降） | 前向生成 token |
| 是否需要梯度 | 需要（反向传播） | 不需要（只前向） |
| 权重是否变化 | 变化 | 冻结 |
| 显存需求 | 权重+梯度+优化器状态（约 20 倍权重） | 权重 + KV Cache + 激活（约 2 倍权重） |
| 瓶颈 | 算力（FLOPS） | 显存带宽 + 延迟 |

### 1.2 推理的两个关键代价

- **预填充（Prefill）**：第一次处理整个 prompt，计算密集（并行）；
- **解码（Decode）**：逐 token 生成，显存带宽密集（串行）。

自回归解码的串行性是延迟的物理根源：生成 $N$ 个 token 需要 $N$ 次前向。

### 1.3 性能指标

| 指标 | 全称 | 含义 |
|------|------|------|
| TTFT | Time To First Token | 收到请求到输出第一个 token 的时间 |
| TPOT | Time Per Output Token | 每个输出 token 的生成时间 |
| 吞吐（Throughput） | tokens/s | 单位时间处理的 token 总量 |
| 并发（Concurrency） | — | 同时处理的请求数 |
| 显存占用 | GB | 模型+KV Cache+激活 |

**直觉公式**：解码速度为 $\text{bandwidth} / \text{参数量}$（每 token 需读取全部权重）。7B 模型 fp16（14GB），在 1.5 TB/s 带宽的 GPU 上约 100 tokens/s 上限。

## 2. 量化（Quantization）

### 2.1 为什么量化

fp16 权重 2 字节/参数，INT8 减半，INT4 减到 1/4。量化换取三样东西：**显存减半/减四倍、推理变快、可用小卡跑大模型**。代价是精度损失。

### 2.2 PTQ：训练后量化

不重训，直接把权重从高精度映射到低精度。对称量化公式：

$$
x_q = \text{round}\left( \frac{x}{s} \right), \quad s = \frac{\max|x|}{2^{b-1}-1}
$$

反量化：$\hat{x} = x_q \cdot s$。误差来源是取整（rounding error）：

$$
\mathbb{E}\left[ (x - \hat{x})^2 \right] = \text{var}(x - x_q) \cdot s^2
$$

| 方法 | 位宽 | 优点 | 缺点 |
|------|------|------|------|
| INT8 PTQ | 8bit | 快、损失小 | 精度略降 |
| FP8（新） | 8bit | 动态范围大 | 依赖新硬件 |
| INT4（GPTQ/AWQ） | 4bit | 显存省 4 倍 | 质量下降，需校准 |
| 4bit（NF4/QLoRA） | 4bit | 块级缩放更稳 | 见 [[03-微调|QLoRA]] |

### 2.3 GPTQ 与 AWQ

两者都是针对 4bit 权重的精度恢复技术，思路互补：

- **GPTQ（逐层 Hessian 补偿）**：基于最优脑曲率近似，量化时按误差最小化逐列更新剩余权重：

$$
\boldsymbol{\delta}_F = -\frac{w_q - w_F}{H^{-1}_{FF}} \cdot \left(H^{-1}\right)_{:,F}
$$

- **AWQ（激活感知）**：观察到**重要通道**（激活幅度大的通道）对精度影响大，按激活重要性对权重缩放再量化，保持关键通道精度。

| 方法 | 核心思想 | 特点 |
|------|----------|------|
| GPTQ | 用二阶信息补偿量化误差 | 需校准集，离线较慢 |
| AWQ | 保护激活显著的通道 | 无需反向传播，快 |
| HQQ | 纯数学近似（不需校准数据） | 零校准集场景 |

### 2.4 KV Cache 量化

KV Cache 随序列线性增长，是长上下文显存大头。KV Cache 量化（INT8/FP8）可将缓存减半，长上下文收益巨大。

### 2.5 精度-速度权衡表

| 配置（7B） | 显存 | 相对速度 | 质量 |
|-----------|------|----------|------|
| FP16 原始 | ~14 GB | 1× | 基准 |
| INT8 | ~7 GB | ~1.3–1.5× | 几乎无损 |
| INT4 (AWQ/GPTQ) | ~4 GB | ~2× | 少量损失 |
| INT4 + KV Cache INT8 | ~3 GB | 更长上下文 | 损失累积 |

> 经验：**7B 以下模型 INT8 几乎无损，INT4 可用；更大模型 INT4 需 AWQ/GPTQ 并实测质量**。量化后一定要跑评估集对比（见 [[../机器学习教程/01-模型评估与交叉验证|模型评估]]）。

## 3. 推理加速技术

### 3.1 KV Cache（已在 01 篇详述）

核心：缓存历史 K/V，避免重复计算。见 [[01-大语言模型原理|LLM 原理]] 4.3。代价：随序列增长占显存。

### 3.2 FlashAttention

标准注意力要先把 $S = QK^T \in \mathbb{R}^{n \times n}$ 存进显存再 softmax（IO 瓶颈）。FlashAttention 用**分块计算 + 在线 softmax**，避免物化整个矩阵：

- 按块计算 $S$ 的部分；
- 用 running max 与 running sum 在线更新 softmax（重新缩放已累积结果）；
- 减少 HBM 读写，加速 2–4×，显存从 $O(n^2)$ 降到 $O(n)$。

### 3.3 vLLM 与 PagedAttention

传统推理引擎为每个请求预分配**连续**的 KV 显存，浪费严重。PagedAttention 仿照操作系统分页：把 KV Cache 切成固定大小的块，**按需分配、物理不连续**：

```
请求1: [块0][块1][块2]         ← 共享/续写时扩展
请求2: [块0][块1]
                     —— 块级管理消除 ~60-80% 显存碎片
```

效果：vLLM 吞吐比 naive 实现高 **2–4 倍**，支持连续批处理（continuous batching）。

### 3.4 投机解码（Speculative Decoding）

用小草稿模型（draft model）先快速猜 $k$ 个 token，大模型一次验证：

- 草稿模型生成候选序列（快、便宜）；
- 大模型并行前向**验证**候选；
- 逐 token 拒绝采样保证**输出分布不变**；
- 命中率高时，大模型一次前向产出多个 token，延迟降低 2–3×。

### 3.5 其他

- **Continuous Batching**：请求动态进出，不等到整批结束；
- **Prefix Caching**：相同 prompt 前缀的 KV 缓存复用（聊天/系统提示）；
- **Tensor Parallelism**：多卡切分权重并行推理。

## 4. 部署框架对比

| 框架 | 定位 | 特性 | 适用 |
|------|------|------|------|
| llama.cpp | C++ 推理 | CPU/边缘运行、GGUF 量化 | 个人/边缘/CPU |
| Ollama | 一键部署 | 内置 llama.cpp、模型管理友好 | 本地体验、快速原型 |
| vLLM | 高性能服务 | PagedAttention、连续批处理、OpenAI 兼容 | 生产 GPU 服务 |
| TGI（HF） | 生产服务 | 服务化完善、量化/张量并行 | Hugging Face 生态生产 |
| TensorRT-LLM | NVIDIA 优化 | 算子级优化、FP8 支持 | NVIDIA 卡极致性能 |
| SGLang | 高性能服务 | 结构化生成优化 | 复杂约束输出 |

### 4.1 如何选

```
个人学习/CPU → Ollama / llama.cpp
单机 GPU 快速原型 → Ollama 或 vLLM
生产多用户 GPU 服务 → vLLM / TGI
极致吞吐 NVIDIA 集群 → TensorRT-LLM
```

## 5. 服务化：OpenAI 兼容 API 与流式输出

### 5.1 OpenAI 兼容协议

主流推理引擎都提供 `/v1/chat/completions` 接口，客户端无缝切换：

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="sk-local")
resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "你好"}],
    stream=True,          # 流式
    max_tokens=512,
    temperature=0.7,
)
for chunk in resp:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)
```

### 5.2 流式输出（SSE）

`stream=True` 走 SSE（Server-Sent Events），逐 token 推送，显著改善 TTFT 感知。前端：

```javascript
// 浏览器端
const res = await fetch("http://localhost:8000/v1/chat/completions", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ model, messages, stream: true }),
});
const reader = res.body.getReader();
// 按 SSE 格式解析 data: {...} 累积输出
```

### 5.3 生产要点

- 批处理与并发限制：控制 `max_num_seqs` 防 OOM；
- 限流与重试：客户端退避重试；
- 超时与队列：SSE 长连接需配置代理超时；
- 监控：TTFT、TPOT、吞吐、显存、GPU 利用率。

## 6. 本地部署 vs API 对比

| 维度 | 本地部署 | 云端 API |
|------|----------|----------|
| 初始成本 | GPU 硬件（数万–数十万） | 0 |
| 边际成本 | 电费 + 折旧 | 按 token 计费 |
| 数据安全 | 完全本地 | 出域（需合规） |
| 延迟 | 网络零延迟，GPU 有限 | 受网络影响 |
| 吞吐/并发 | 受本地硬件限制 | 可弹性扩展 |
| 模型选择 | 开源模型（天花板有限） | 闭源旗舰 + 开源 |
| 维护成本 | 部署、升级、运维 | 服务商负责 |
| 适合 | 高并发/隐私/成本规模 | 快速验证/低频/旗舰模型 |

**决策矩阵**：
- 私有数据、合规要求 → 本地；
- 小规模、快速迭代 → API；
- 规模化生产 → 本地 + API 混合（本地跑开源长驻，API 兜底）。

```bash

ollama pull qwen2.5:7b          # 拉模型

### 7.2 vLLM 生产服务

# 客户端：与 5.1 完全一致，切换 base_url 即可

from openai import AsyncOpenAI
import asyncio

async def main():
    client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="sk")
    stream = await client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct",

        if d:
            print(d, end="", flush=True)

asyncio.run(main())
```

### 7.3 压测吞吐（简单版）

```python
import time, threading
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="sk")
N = 8
results = []
def worker(i):
    t0 = time.time()
    client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct",
        messages=[{"role": "user", "content": "讲一个 100 字的笑话"}],
        max_tokens=200,
    )
    results.append(time.time() - t0)

threads = [threading.Thread(target=worker, args=(i,)) for i in range(N)]
[t.start() for t in threads]; [t.join() for t in threads]
print(f"并发 {N}，平均耗时 {sum(results)/len(results):.2f}s")  # 正式压测请用 wrk/loadgen
```

## 8. 部署排查速查

| 症状 | 可能原因 | 排查 |
|------|----------|------|
| OOM | KV Cache 超限/量化不足 | 减 `max-model-len`、加量化 |
| 首 token 慢 | 预填充长 prompt、热启动 | 预填充优化、prefix cache |
| 吞吐低 | 无连续批处理、碎片 | 换 vLLM、调 batch |
| 质量下降 | 量化过度 | 回退 INT8/FP16、重测评估集 |
| 流式不输出 | 代理缓冲 | 禁用代理缓冲、设 SSE 支持 |
